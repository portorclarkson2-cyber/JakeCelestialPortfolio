06 / PROBLEM-SOLVING

Five cases. One
repeatable process.

Use the same structure for each real troubleshooting experience: symptom → possible cause → diagnosis → fix → verification → lesson.

CASE 01

Database / API response error

Symptom: Data expected as JSON is not returned correctly.

Diagnosis: Check browser Network/Console output, server logs, endpoint, and database operation.

Fix & lesson: Correct the failing endpoint or database issue, then test the full request again.

CASE 02

SQLite database locked

Symptom: A database operation reports that the database is locked.

Diagnosis: Check open database sessions, server connections, and unfinished transactions.

Fix & lesson: Close unnecessary connections and retry after confirming the server/database state.

CASE 03

Wrong account data

Symptom: Different users appear to share profile/order information.

Diagnosis: Trace the current-user object and storage/database key from login to each page.

Fix & lesson: Scope stored records to the logged-in account and test with two accounts.

CASE 04

Android image not displayed

Symptom: The expected object image does not appear.

Diagnosis: Check the drawable resource, filename, resource ID, and ImageView reference.

Fix & lesson: Correct the resource reference and rebuild/test the alphabet sequence.

CASE 05

Responsive layout issue

Symptom: A section overflows or becomes difficult to use on a smaller screen.

Diagnosis: Inspect fixed widths, gaps, flex/grid behavior, and mobile breakpoints.

Fix & lesson: Add responsive rules and retest at several viewport widths.

Prevention.

Problem

Applications can become vulnerable when user-controlled input is directly combined with SQL commands.

Risk

Unsafe query construction can allow unintended database operations or data exposure.

Defensive approach

Use parameterized/prepared statements, validate input, apply least privilege, and handle errors safely.
